# Prior art for the four remaining gaps — and the premise error it exposed

Method: 28 parallel search angles (academia, vendor docs, GitHub, patents, and developer communities in
Chinese, Japanese, Korean, Russian, German, French, Spanish, Portuguese and English) returned 408 leads,
385 of them opened. Every claim below was then re-verified by hand, either against this machine's own
source tree and run archive or by fetching the primary source. Anything not verified twice is marked.

## The finding that reframes everything

We feed the tracker 1920x1440 and detect corners on every frame. Nobody else does either.

| system | what its tracker actually consumes | source |
|---|---|---|
| XRSLAM (the code we ported), upstream iOS app | **640x480 @ 30 fps**, detection every **3rd** frame | `xrslam-ios/visualizer/src/Camera.swift:28` (`preset: .vga640x480`); `xrslam-ios/visualizer/configs/slam_params.yaml` (`sliding_window: tracker_frequent: 3`, `max_keypoint_detection: 300`) — read in our own copy of rev 4beb1a9 |
| RD-VIO (the algorithm inside XRSLAM, same lab) | 640x480 @ 30 Hz on an iPhone X; all-frame average 18.38 ms on a desktop i7-7700 | [arXiv 2310.15072](https://arxiv.org/abs/2310.15072) §4.4.4, Table 2 |
| ARCore | "a 640x480 (or 640x360 on some devices) ImageReader to supply our motion tracking engine, and a nominally 1920x1080 SurfaceTexture to provide the background image for rendering" | Google engineer @inio, [arcore-android-sdk#667](https://github.com/google-ar/arcore-android-sdk/issues/667), read via the GitHub API |
| Android CameraX | `ImageAnalysis` defaults to 640x480 with `STRATEGY_KEEP_ONLY_LATEST` | `androidx/camera-core/ImageAnalysis.java` |
| ARKit | 1920x1440 is the **2x2-binned** stream, binned in the capture path "to reduce memory consumption and processing power"; and it "can skip the computer vision processing for some of those frames" | [WWDC22 10126](https://developer.apple.com/videos/play/wwdc2022/10126/); [WWDC18 610](https://developer.apple.com/videos/play/wwdc2018/610/) |

Our detection gate exists in the code we compiled and we never turned it on:
`feature_tracker.cpp` computes `slidind_window_frame_tag = !is_initialized || frame->id() % config->sliding_window_tracker_frequent() == 0`
and calls `frame->detect_keypoints()` only under it. Compiled-in default is 1 (`config.cpp:78`); upstream's
iOS config sets 3; our bench YAML sets neither. So we run ~9x the pixels and 3x the detections of the
configuration upstream ships for this exact phone — about **27x upstream's front-end pixel throughput**.

## We already measured the consequence and filed it wrong

`run-1e7422d3` (600 s live, 640x480, tracker_frequent 2, CPU engine, no GPU front end), from this
machine's own archive:

| | that run | ARKit reference | our current 1920x1440 GPU arm |
|---|---|---|---|
| thermal | **nominal for all 602 samples** | 0 s serious | 173 s serious |
| footprint peak | **47 MB** | 266 MB | 276 MB |
| CPU cores | **0.52** | 0.80 | 0.80 |
| p95 latency | 40 ms | 55 ms | 42 ms |
| first pose | 566 s (operator stationary; run ended non-finite) | 1.5 s | 3.6 s |

P2 and P3 are already solved at VGA — by a factor of 5.7 on memory — and were dismissed in the log as
"resolution is lossy, not a shipping lever". The prior-art sweep says that premise is wrong: tracking at
a fraction of the display resolution is what ARKit, ARCore, CameraX and upstream XRSLAM all do. The
lossless rule we adopted governs the GPU port's fidelity to the CPU path; it never required feeding the
tracker the display stream.

## P1 — pose rate 28.4/s vs 59.9/s: two separable halves

**(a) Delivery rate is not vision rate.** Apple, verbatim (WWDC18 610): "By combining those both systems
World Tracking can skip the computer vision processing for some of those frames, while still keeping an
efficient and responsive tracking… the results are returned in ARFrames at 60 frames per second." So
ARKit's 59.9 poses/s is IMU propagation between visual updates, not 60 visual updates.

XRSLAM has the same mechanism already: `XRSLAM::Detail::get_latest_pose()` (`detail.cpp:146-160`) takes
the latest optimized state and propagates it through `frontal_imus` with `propagate_state()`, and
`XRSLAMGetResult(XRSLAM_RESULT_BODY_POSE)` exposes it. Our bench never calls it — `xrslam_bench_poll_result`
emits one result per pushed image, so our pose rate is the visual frame rate by construction. Polling the
propagated pose on a 60 Hz timer is the like-for-like comparison, and it is a bench/bridge change with no
engine change.

**(b) Visual rate.** At 640x480 with detection every 3rd frame the front-end cost falls ~27x, which is
what makes a 60 fps visual channel arguable at all. Note the algorithm's own authors measure 18.38 ms
all-frame average on a desktop i7-7700 — RD-VIO was never a 60 Hz design.

## P2 — power: the ceiling, quantified

Navion (MIT, JSSC 2019 / VLSI 2018) implements exactly this front end (pyramidal LK every frame, detection
at keyframes) and publishes the comparison: ARM CPU **2.33 W** at 5 fps on the vision front end, FPGA
1.46 W, the ASIC **24 mW** at 752x480. No WGSL kernel work closes a gap of that shape; pixels and frames
do. Also, the comparison itself needs a condition: at thermalState `.serious` iOS "lower[s] the frame rate
of ARKit apps" (WWDC19 422) — an arm at 173 s serious and an arm at 0 s serious were not run under the
same system policy, so every verdict should report both arms' thermal dwell.

## P4 — first pose 3.6 s: floor from our own source, knobs are upstream's

`initializer.cpp:26-38` returns early until `keyframe_gap * (keyframe_num - 1) = 5 * 7 = 35` frames of
history exist — 1.17 s at 30 fps before the first bootstrap attempt, then >=10 px mean parallax, >=50
matches, >=30 landmarks (`config.cpp:38-48`). All of these are YAML-settable through
`yaml_config.cpp:281-307` (`initializer.keyframe_num`, `.keyframe_gap`, `.min_parallax`, …) — upstream
knobs, not inventions.

- **XR-VIO** (arXiv 2502.01297, same lab lineage, deployed on iPhone 13 Pro at 640x480/30 Hz) initialises
  from **4 keyframes spaced 0.1 s — a 0.3 s window** — with 83.98 % success and 0.026 m ATE on EuRoC.
  No code released, so it justifies knob values; it is not something we can copy.
- **Kimera-VIO** (MIT SPARK, **BSD-2**, verified) has `src/initial/InitializationFromImu.cpp` (gravity-aligned
  IMU-only initial state and bias guess) and gates detection on keyframes in `StereoVisionImuFrontend.cpp`
  while tracking every frame. This is the copyable source if we want a motion-aware keyframe policy
  instead of XRSLAM's modulo-N.
- **OpenVINS** static and dynamic initialisers are **GPL-3.0** (verified on the file header) — unusable.
  Same for HybVIO/Spectacular AI (GPLv3), ORB-SLAM, VINS, DSO, SVO.

## What nobody has done

No prior art was found for a bit-exact WGSL/WebGPU replication of an OpenCV front end for VIO on a phone —
that part appears to be ours alone. No permissively-licensed implementation of sub-second VIO
initialisation was found; XR-VIO publishes the method without code. No source was found claiming mobile-GPU
corner detection beats a NEON CPU at VGA; the one careful GPU-front-end measurement (Faster than FAST,
IROS 2020) is on a Tegra X2 where OpenCV's own CUDA tracker was **slower** than the CPU (3.96 ms vs 1.88 ms).
