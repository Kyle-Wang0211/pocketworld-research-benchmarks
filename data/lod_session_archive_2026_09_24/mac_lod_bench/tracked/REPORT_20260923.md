## 0. 一句话结论

**桌面结论在移动 TBDR 上「方向成立、量级不成立」。**

顶点展开确实更快,可复现、可归因、输出逐字节相同;但 A16 上的效应是 **1.5%–9%**,不是桌面证据里的 **9 倍**(656 ms vs 72 ms)。这一刀值得挥(免费、无风险、两条路都受益),但它**不是**那个能决定臂 A / 臂 B 走向的量级。

> ⚠️ **采用它的理由是「免费 + 上游都这么写 + 实测不倒退」,不是「实测快 6–9%」。**
> 6–9% 这个数字只在一颗 GPU 上量过,**不得当作三端的数字引用**。见 §0.5 与限制 3。
>
> ✅ **跨端判据(用户 2026-09-23 拍板)= 「代码无平台专属」,不是「每端都实测过」。** 本改动新增 `#if defined(__APPLE__)` 0 处、厂商专属 API 0 处 ⇒ **按这条判据已达标**,安卓实测延后不阻塞。

## 0.5 先说清楚:这不是给苹果做的设计

**TBDR(分块延迟渲染)不是苹果的东西。** 高通 Adreno、ARM Mali、华为 Maleoon、Imagination PowerVR、苹果,移动端**全是**分块架构;桌面的 NVIDIA / AMD 才是立即模式。所以"桌面 vs 移动"是真实的架构分界线,而"苹果 vs 其他"不是 —— §2.2c 那三条证据之所以可疑,是因为它们全在**桌面**测的,不是因为它们不在苹果上测的。

改动本身**零平台专属成分**:

| | |
|---|---|
| 改的东西 | 一个 `.wgsl` 文件 + 一行 `wgpuRenderPassEncoderDraw` |
| 走的路 | Dawn / WebGPU,iOS + Android + 鸿蒙**同一份代码** |
| 新增 `#if defined(__APPLE__)` | **0 处** |
| 新增 Metal / 苹果专属 API | **0 处** |

台架本身也没有苹果图形 API:渲染到离屏纹理再读回,全程只调 WebGPU 的 C API。苹果的只有外壳三样 —— SwiftUI 窗口、`CommonCrypto` 算 sha256、`NSFileManager` 写文件。换成 NDK 外壳即可在安卓跑,**两条臂的 shader 与 draw 调用一字不改**。

(澄清:生产渲染器里 `scene_iosurface_renderer.cpp:1458` 那句 `#if !defined(__APPLE__) → return nullptr` 挡的是 **IOSurface 零拷贝上屏**,不是 WebGPU 本身。本台架不走 IOSurface,不受它挡。)

## 1. 做了什么

改动就是 §2.2c 写的三行:

| | 改前(臂 A) | 改后(臂 B) |
|---|---|---|
| host | `draw(6, N)` | `draw(6 * N, 1)` |
| WGSL 签名 | `vs_main(vi, @builtin(instance_index) ii)` | `vs_main(vi)` + `let ii = vi / 6u` |
| 角点 | `offsets[vi]` | `offsets[vi % 6u]` |

两版 shader 的 sha256 都记进了结果 JSON,台架里烧的是**改前/改后生产文件的逐字副本**,不是手写的近似。

顺带在分支上修了一处会**静默**的回归:四个 splat 冒烟工具还在用 `draw(6, kNumSplats)`。换上展开版 shader 后它们只画第 0 个 splat —— 而四个测试 splat 同心,**中心像素断言照样通过**。是覆盖面悄悄掉到 1/4,不是测试变红。

## 2. 实验怎么排的(以及为什么这么排)

手机上做性能 A/B,最容易把结论做废的是**热漂移**:先连跑 A 再连跑 B,就把「臂」和「机身温度」彻底混杂了。这次的排法:

- **三个标签循环轮换**:`A`(instancing)、`B`(顶点展开)、`A′`(**还是 instancing**,只是换个位置跑)。每轮三块的次序按轮号循环旋转,R=9 时每个标签在首/中/末位各出现 3 次 —— 块内位置效应在标签之间完全平衡。
- **`A′` 是整个设计里最关键的一条**。它和 A 是同一条 pipeline、同一个 draw,所以 `A′/A` 量到的任何偏离 1.0 都是**这套 A/B 机器自己分辨不了的部分**。没有它,我没法判断「B 快 9%」是信号还是流程噪声。
- **轮 = 重复单位**。一轮里的 50 帧是伪重复,不是「臂」的独立重复;所有统计都做在 9 个轮中位数上。
- **阳性对照**:同一把尺子量 A 在 N 和 N/2。量不出「活儿少一半」,这把尺子就不配报任何零结果。
- **正确性对照**:两臂的整张帧缓冲(1179×2556 RGBA8)做 sha256 比对。

主判据是 **GPU 时间戳的 p50**(A16 支持 `timestamp-query`,已确认),壁钟 p50 作交叉校验。

台架的渲染配置逐项照抄生产 splat pass(`scene_iosurface_renderer.cpp:555-585`):RGBA8Unorm + premultiplied OVER 混合、Depth32Float **只读**测试、`cullMode=None`、零顶点缓冲的 storage 拉取、每帧 submit 后等 `OnSubmittedWorkDone`。

## 3. 结果

**主结果 —— GPU 时间戳 p50 的逐轮配对比值 `B/A`(<1 = 顶点展开更快)**

| 格子 | N | quad 半径 | run1 B/A | run2 B/A | **两跑均值** | 噪声底 \|1−A′/A\| | B 胜轮次 |
|---|---:|---:|---:|---:|---:|---:|:-:|
| `N250k_r1.5` | 250,000 | 1.50 px | 0.9080 | 0.9080 | **+9.2%** | 0.00% | 9/9 · 9/9 |
| `N1M_r1.5` | 1,000,000 | 1.50 px | 0.9382 | 0.9241 | **+6.9%** | 0.00% | 6/9 · 9/9 |
| `N4M_r1.5` | 4,000,000 | 1.50 px | 0.9380 | 0.9050 | **+7.9%** | 0.46% | 9/9 · 9/9 |
| `N1M_r4.0` | 1,000,000 | 4.00 px | 0.9850 | 0.9718 | **+2.2%** | 0.40% | 9/9 · 8/9 |
| `N4M_r0.75` | 4,000,000 | 0.75 px | 0.9317 | 0.8930 | **+8.8%** | 0.68% | 9/9 · 9/9 |

符号检验:4/5 格两跑都是 p=0.0039(n=9 的最小可能值)。`N1M_r1.5` run1 是 6/9(p=0.125)、run2 是 9/9 —— run1 那一格噪声偏大,见限制 5。
壁钟 p50 与 GPU 同向,B/A 在 0.894–0.983 之间。

**对照**

| 对照 | 口径 | 结果 |
|---|---|---|
| 阳性(尺子能不能量出差别) | A 在 N vs N/2 的 GPU p50 | **10/10 PASS**,比值 0.30–0.64 |
| 正确性(改对了没有) | 整张 1179×2556 RGBA8 帧缓冲 sha256 | **两跑都逐字节相同,差异 0 字节** |
| 噪声底(流程本身的分辨率) | `A′/A`,同 pipeline 换位置复跑 | **0.00%–0.68%** |
| Dawn 校验错误 | `uncapturedErrorCallback` | 两跑都为空 |

> 正确性对照还**附带证明了绑对了 shader**:假如臂 B 挂的还是 instancing 版,`draw(6N,1)` 下 `instance_index` 恒为 0(只画 `splats[order[0]]` 一个点),而 `offsets[vi]` 的下标冲到 6N 后被 WGSL 钳到 `offsets[5]` —— 一个 quad 的 6 个顶点全塌到同一个角,退化成零面积三角形,**画面会是全黑**。两臂输出逐字节相同 ⇒ 臂 B 确实在用 `vi / 6u` 和 `vi % 6u`。

**绝对帧时间(run2,较凉的一跑)**

| 格子 | A instancing GPU p50 | B 顶点展开 GPU p50 | B 壁钟 p50 | 折算 fps |
|---|---:|---:|---:|---:|
| `N250k_r1.5` | 5.7 ms | **5.2 ms** | 6.4 ms | 193.2 |
| `N1M_r1.5` | 25.0 ms | **23.1 ms** | 24.2 ms | 43.2 |
| `N4M_r1.5` | 114.2 ms | **102.7 ms** | 104.1 ms | 9.7 |
| `N1M_r4.0` | 37.2 ms | **36.1 ms** | 37.3 ms | 27.7 |
| `N4M_r0.75` | 156.2 ms | **135.9 ms** | 137.4 ms | 7.4 |

⚠️ 见限制 2:这是**上界**,不是点云路的预算。

### 3.1 ✅ 排序 indirection 定价 —— 以及它**不是**更大的那条鱼

做完 A/B 之后立刻要问的是:**draw 拓扑到底是不是这条路上最大的一笔?** 生产里 `order[]` 是深度排序的置换,`splats[order[ii]]` 因此是对 144 MB buffer 的**随机读**;点云路做完 §8 第 2 步「删排序」之后就是顺序读。如果那个 indirection 值几倍,那 6–9% 就只是零头,**我等于在指错优化方向**。

**第一次做法失败了,而且失败在我事先标出的那个位置。** run3 把「乱序 / 顺序」放成两个**格子**:乱序格第 3 位、顺序格最后一位。结果顺序格比乱序格慢 10–15%(机制上讲不通 —— 连续读不可能输给随机读),而顺序格**开局就是 113 ms**,乱序格整格只漂 +1.1% 落在 99 ms。差值与累积热漂移同号同量级,**分不开 ⇒ 按事先写死的规矩作废**。

**改成 2×2 析因重做**(run4 / run5):五个标签在**轮内**循环轮换 —— `A_shuf`、`B_shuf`、`A2_shuf`(噪声底)、`A_seq`、`B_seq`。两个 `order` buffer 常驻,切换只换 bind group、不做任何拷贝。这样热漂移对**每一组对比**同等平衡,不再只有 A/B 受保护。

| 对比 | N=1M(run4,R=10) | N=4M(run5,R=5) |
|---|---:|---:|
| 噪声底 `A2_shuf / A_shuf` | **0.13%** | 2.68% |
| **draw 拓扑**(乱序 order 下) | **快 7.6%**,10/10,p=0.0020 | **快 7.7%**,5/5 |
| **draw 拓扑**(顺序 order 下) | **快 9.6%**,10/10,p=0.0020 | **快 12.0%**,5/5 |
| order 访存(instancing 下) | 快 0.9%,7/10,p=0.18 ⇒ 无效应 | **慢 3.6%**,0/5 |
| order 访存(顶点展开下) | 快 2.9%,9/10,p=0.0039 | 快 0.6%,3/5 ⇒ 无 |
| 两项合计 | 快 10.2%,10/10 | 快 7.9%,5/5 |

> ⚠️ **R=5 时符号检验的 p 下限就是 0.0625**(2/2⁵),p<0.05 在那一跑里**结构上不可能达到**。4M 列的判据因此是「5/5 全胜 + 全距不跨 1.0 + 远高于噪声底」,不是 p 值。

**🔴 结论:排序 indirection 不是更大的那条鱼。** 它在 1M 上值 0.9%–2.9%、在 4M 上是 0 甚至略负;draw 拓扑在两个规模上都稳定在 7.7%–12%。**在这份台架里,draw 拓扑就是两者中更大的那个。** 我先前挂的那条红字警告(「在它出数前别把 6–9% 当成最大的一笔」)到此解除。

**⚠️ 一个线索,不是结论**:4M 上顺序访存反而**慢** 3.6%(5 轮全负,全距 [1.027, 1.073]),方向与 run3 那个被判为热漂移的结果一致 ⇒ 可能有真成分。一个可能的机制是连续 36 字节记录让并发线程挤在窄地址区造成 DRAM bank/通道冲突,而随机访问反把负载摊开。但它只比 2.68% 的噪声底高一点点,**记成线索,不当结论**。

**🎓 顺带:阳性对照当场抓到一次坏测量。** run4 的 4M 格用 5 标签 × 10 轮 × 50 帧 ≈ 2500 帧满载,机器彻底降频 —— 五个标签全漂 **+81%~+100%**(109 → 210 ms)、噪声底涨到 4.19%,而**阳性对照 N/2 ÷ N = 0.923**(应 ≈0.5):活儿砍一半机器也快不了,说明它已经被降频卡死而不是被工作量卡住。按事先写死的规矩**整格作废**,冷机 + 负载砍到 1/4(K=25, R=5)重跑,阳性对照回到 0.513 才取数。**没有这条对照,那一格 +7.1% 的数字会被我当成结果报出去。**


## 4. 判读

**(a) 效应是真的。** 噪声底 `A′/A` 稳在 1.00 附近,而 `B/A` 的中位数在 0.91–0.99;多数格子是 **9/9 轮 B 全胜**(符号检验 p=0.0039,n=9 能给出的最小值)。两次独立 run 同向。

**(b) 归因干净 —— 而且有一条反向论证。** 臂 B 的 shader 比臂 A **严格多做事**(每个顶点多一次整除 + 取模),它还是更快。所以这个收益**不可能**来自「shader 变便宜了」,只能来自顶点阶段怎么被调度。

**(c) 机制预测被印证。** 效应量随 quad 变小而单调变大 —— 4.0 px(片元受限)几乎没有,1.5 px 和 0.75 px(顶点受限)最大。这正是 warp/SIMD 占用率论点该有的形状,而不是一个到处一样大的常数偏移。

**(d) 但量级差了一个数量级。** 桌面证据是 656 ms vs 72 ms(9 倍);实测是 1.5%–9%。最直白的解释:**这颗 GPU 的驱动本来就把小实例跨实例打包进同一个 SIMD group,做得比 `magcius` 描述的 NVIDIA 路径好得多**,所以只剩一点零头。⚠️ 这一句是【推断】,我没有任何移动 GPU 的 SIMD 调度一手资料;而且**这个解释是否适用于 Adreno / Mali / Maleoon,同样零证据**。

## 5. 诚实的限制

1. **合成数据,不是真高斯场景。** 位置是屏幕上的均匀随机,conic 是常数。好处是能把 quad 半径当自变量扫;代价是它不复刻真实场景的空间聚簇。
2. **绝对帧时间偏悲观,不能直接当点云路的预算。** 台架跑的是**高斯**配置:alpha 混合 + `discard`(两者都关掉 TBDR 的隐面剔除)、加上乱序 `order[]` 带来的随机访存。§8 第 2 步要做的「删排序 + 开深度写」正是把这两项拿掉。所以表里的绝对数是**上界**。
3. 🔴 **数字只来自一台 A16。** Adreno / Mali / Maleoon 上效应是更大、更小还是反向,**零证据**。
   ⇒ 因此本报告**只**支撑三条:① 桌面那个 9 倍在移动端不成立;② 这个改动在移动端不是回归;③ 它零平台专属、零风险,且 rerun / Potree-Next 本来就这么写。
   ⇒ 它**不**支撑「顶点展开在三端都快 6–9%」—— **6–9% 是一台设备的数字,引用时必须带着这句。**
   ✅ **用户 2026-09-23 拍板:跨端的判据是「代码无平台专属」,不是「每端都实测过」**(原话「安卓以后再说,理论上可跨端就可以了」)⇒ 本条是**已知并接受的限制,不是阻塞项**。安卓实测延后,不是前置条件。
   📌 真要补时路已铺好:`~/Developer/dawn-android-arm64/src/dawn/native/libwebgpu_dawn.a` 已编好,台架换个 NDK 外壳即可,两条臂的 shader 与 draw 一字不改。
4. **`A′/A` 只覆盖了「同 pipeline 换位置」这一种噪声**,不覆盖跨进程、跨次启动的差异。
5. 第一次 run 的最后一格出现过一次 **1.8× 的断崖**,三条臂同步掉 —— 判为设备级状态切换(多半是自动锁屏让出了合成器)。第二次 run 已把屏幕状态钉死。因为比值是在轮内算的,这个断崖不污染结论;但它是这台设备会出现的真实噪声源,记在这里。

## 6. 这对调研报告意味着什么

- **§8 第 0 步的两个预设分支都没有干净地命中。** 原文写的是「有明显提升 ⇒ 1px compute 方向被独立印证 / 毫无变化 ⇒ 臂 B 权重上调」。实际落在中间:提升是真的但很小 ⇒ **instancing 陷阱不再是臂 A vs 臂 B 的判据**,这个选择得回到画质、许可、栈风险上去做。严格说这**略微抬高**臂 B(顶点展开 quad 路)的权重 —— 桌面证据担心的那个坑在 A16 上基本不存在,而且无论如何都可以直接用顶点展开绕开。
- **U11(「A16 上零一手点云帧率实测」)不再是空白**,但填进去的数字比 §4.3 的推断难看得多,见限制 2。
- ✅ **「排序 indirection 会不会更贵」已经量了(§3.1),答案是不会**:1M 上 0.9%–2.9%、4M 上 ~0,而 draw 拓扑两个规模都是 7.7%–12%。⇒ **在这份台架里 draw 拓扑是两者中更大的那个**,先前那条红字警告解除。下一件该量的是**真实场景数据**(合成的均匀随机不复刻空间聚簇)和**另一家移动 GPU**。
