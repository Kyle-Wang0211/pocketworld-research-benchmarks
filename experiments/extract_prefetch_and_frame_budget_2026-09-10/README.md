## 三、提取预取(EXTRACT_PREFETCH)判死 —— 真因不是「目标不可预测」

08-09 的判决写的是「拍摄期形态判死,复活条件=排空期 FIFO 可预测」。09-09 段账显示排空期
112 s,条件成立,于是重开。实测(PF-DIAG 两侧摘要探针):

```
enqueue digest=8081...
adopt   digest=8685... have valid=0 w=0 h=0 digest=0   ← 第1帧必然未命中
enqueue digest=6086...
adopt   digest=8081... have valid=0 w=0 h=0 digest=0   ← 第2帧摘要本该匹配,手上却是空的
```

- **摘要守卫没问题**(adopt 与上一次 enqueue 的 digest 完全一致,顺序也对)。
- **`pf_result` 从来没被生产出来**(`valid=0 digest=0`)。
- 机制:**预取队列深度 1,且「未命中转发」与「预取」共用同一个槽**。第 1 帧必然未命中 →
  转发时把当前帧塞进那个槽 → 顶掉刚排进去的下一帧预取 → 第 2 帧又空 → **第一次未命中自我延续**。
- ⇒ **任何调用顺序都不可能命中**(add_frame 前/后两种位置都实测,均 `pf=3` 30/30)。
- 代价:预取线程白做一遍 ⇒ 实测 **stream_ms 10814 → 11747(−8.6%)**。

**生产不受影响**:该 env 默认关、设备实测 env 里没有它、生产 89 帧 `pf` 全 0。
这是**未出货功能里的休眠缺陷**,不是在跑的 bug。但**修它就是拿那 29% 的前提**。
