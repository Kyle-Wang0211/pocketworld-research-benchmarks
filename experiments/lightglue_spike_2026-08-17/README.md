## 二、结论

### ✅ 自适应剪枝 = 唯一拿到的真提速,可以收
`depth_confidence=0.95 / width_confidence=0.99`(官方默认,我们一直写死 −1 关着)。
逐对交替 A/B(同进程同特征,每对内部交换先后):**M3 上 1.875×,5090 上 1.566×**,
提前退出层中位 7/9。

匹配**集合**不是无损(Jaccard 中位 0.83,B2 的匹配丢 9.4% 又补进等量新匹配,
数量只差 0.3% —— **数量骗人**),但**重建层近乎无损**:点 −0.17%、观测 −0.76%、
132/132 帧全注册、重投影反而更好。参照系:换后端造成的点数差就有 0.4%,比它还大。

⚠️ MPS 上剪枝会让每层 `index_select` 的张量形状逐对变化,缓存分配器复用不了块 ⇒
池子无界涨,实测 swap 冲到 14.3GB、单对 3.5s→10s(**量到的是换页不是算法**)。CUDA 上不存在。

### ✅ fp16 提取 = 无损,内存减半
中间张量 0.92GB→0.46GB,提取 34→20 ms/帧。重建层:点 −0.13%、观测 −0.07%、
轨迹与 ≥3 观测**逐位相同**、重投影略好。
⚠️ 只降**提取端**,描述子出来立刻转回 fp32 喂匹配器。**匹配器** fp16 是另一件事(见待办)。

### ⚰️ RaCo 三个变体全部判负
- **排序器**:轨迹 4.74→4.57、观测 −5.4%,四项跌三项。上游 `RankerMode.auto` 在 ≥3072
  时自己就 bypass,原来不只是为了省时间。
- **协方差头**(dynamo 的加载器把那 5 个张量丢掉了,我们接了回来,结构逐字抄 cvg/RaCo:
  `Conv2d(128,64,3)→LeakyReLU→…→Conv2d(32,3,1)`,softplus 只作用在 L11/L22,Σ=LLᵀ):
  重投影 1.5266→**1.5106**(全场最低),但靠的是扔掉 σ 大的点,而那些点在边缘弱纹理区 ⇒
  覆盖 1.16×→1.08×。**它换来"更准",代价正好是我们最在意的"覆盖"。**
  ⚠️ 激活是 **LeakyReLU 不是 SELU**(主干和 score/ranker 头都是 SELU,按一致性去推会推错)。
- **RaCo 本体**:铺得广(覆盖 2.553×)但扎得浅(轨迹 4.69 vs B2 的 5.44,≥3 观测低 4pp),
  且剪枝在它身上省不动(停在 8.75/9,只有 1.4×)。

### ⚰️ 抬分辨率:买"实"不买"广"
1600→2432→3200:轨迹 5.44→5.64→5.59、重投影 1.5502→1.5313→**1.5135**,
但**覆盖 2.042→1.756→1.644 反而下降**,点/格 3.43→3.86、k近邻 0.0307→0.0278。
高分辨率是在已有纹理处挖细节,不是够到新地方。

### ⚰️ 分块 ALIKED:病因不是 align_corners
逐分支偏差 x1(全分辨率) 2.8e-4 → x2_up(÷2) 3.2e-3 → x3_up(÷8) 8.8e-3 → **x4_up(÷32) 1.9e-2**,
÷32 分支是全分辨率分支的 **67 倍**。halo 32 到 /32 层只剩 1 像素上下文,upsample32 再把误差
摊到 32×32 像素块上。
⚠️ 我先猜是 `align_corners=True` 的全局坐标映射,**换成 False 几乎没变化(93.9%→88.0%),假设被证伪**。
收敛到余弦 0.9998 需 **halo 512px**:1600 档单块比整张图还大;4224 档可行但提取算力 **4.4–7.7×**。

## 三、三道墙(为什么 ALIKED 上不了手机)

1. **算力**:LightGlue@8192 剪枝后 1.381 TFLOP/对,是生产暴力匹配(0.0172 TFLOP)的 **80 倍**。
   A16 ~2.0 TFLOPS fp32、按 35% 有效利用率 ⇒ **1973 ms/对,1516 对 = 49.9 分钟**(生产 77 秒)。
   唯一有量级的旋钮是关键点预算(N² 缩放),但 @2048 时臂A 的匹配比值掉到 **0.892×**——连基线都不如。
2. **内存**:ALIKED 主干产出 `[1,128,H,W]`,**每像素一个 128 维向量**(与输出点云的稀疏/稠密无关)。
   4224 档单这一张 6.38GB;fp16 + 1600 档可压到 0.46GB。
3. **权重**:`assert desc0.shape[-1] == self.conf.input_dim` ⇒ ALIKED-t16(64维)直接跑不起来。
   官方 LightGlue 六个变体只有 superpoint 是 256,其余全 128,**没有 64 维** ⇒
   t16 / XFeat(64d) / EdgePoint2(32–64d) 全部要连带重训匹配器。

## 四、代码

`code/` 下全部脚本。关键的几个:

- `lg_sift_arm.py` —— 臂A:复用 DB 里的生产 DSP-SIFT 关键点/描述子,只换匹配器
- `lg_aliked_arm.py` —— B2 系:整条前端换 ALIKED(`--model` 选变体、`--extract-amp` 走 fp16 提取)
- `lg_raco_arm.py` —— RaCo 系(`--ranker` / `--select cov`)
- `raco_cov.py` —— 把 dynamo 丢掉的 RaCo 协方差头接回来
- `chunked_attn.py` / `chunked_assign.py` —— 两把无损内存刀(bit-identical;CUDA 上无用,是为 18GB 统一内存打的)
- `probe_pruning.py` —— 逐对交替 A/B 探针(单场对比噪声地板 18% > 效应,必须交替)
- `coverage_metric.py` —— 覆盖(占据体素)与形状(k近邻/轨迹)两把尺子
- `downstream.py` —— 所有臂共用的几何验证 + 增量建图 + 指标

⚠️ `lg_load.py` 把 LightGlue 子模块挂在合成包 `lgx` 下加载,绕开 `__init__.py`
(它 import pycolmap,而 torch+pycolmap 同进程 = OMP Error #15 ⇒ 匹配与建图必须分进程)。

🔴 `lg_raco_arm.py` 里 `topk_chunk_size=None` 不能改:上游为 TensorRT 写的 `_chunked_topk`
在 MPS 上遇到「绝大多数是 −inf」的张量会整块返回 −inf,关键点全落第 0 行、匹配恒为 0,**零报错**。

## 五、待办

- **匹配器 fp16 的重建层复验**。早先只按匹配集合漂移 6% 就否掉了 —— 而剪枝那次证明
  集合漂移 17% 仍可重建无损。这个否决**可能是错的**,若成立则 A16 的 ANE(~8–17 TOPS)可用。
- TF32 的显式 A/B(`cudnn.allow_tf32` 出厂是 True,已在 `devutil.strict_fp32()` 里关掉)
- 配对数是否可随匹配质量提升而减少(1516 对是按暴力匹配的口径定的)

# 第二轮(08-17 晚):上机可行性 + 算力压缩

## 🔑 表面粗糙度 —— 唯一能复现用户肉眼判浮点的尺子

局部 PCA(k=15 邻域,最小特征值开方 = 沿法线的 RMS 宽度),`local_roughness.py`:

| 臂 | 粗糙度中位 | >20mm 占比 |
|---|---|---|
| **ALIKED@16384** | **8.95mm** | **10.32%** |
| 基线(生产) | 12.20mm | 18.83% |
| 臂A | 12.57mm | 19.58% |
| **LoFTR** | **15.39mm** | **30.51%** |

**排序与用户肉眼完全一致。** 前两把尺子全部失手,必须记下来:
- **视差角+track 长度**(`floater_risk.py`):判 LoFTR 风险点(1,355)比 ALIKED(1,961)**还少**,与所见相反。
  失手原因:镜像鬼点/重复纹理产出的是"**多视一致但错误**"的点 —— 骗过判据的机制正是"看起来被多视角验证过"。
- **空间孤立度**(`isolation_check.py`):四臂占比几乎相同(3.13–3.48%),LoFTR 甚至最低。
  失手原因:用户说的不是孤立飞点,是**一整片致密但偏离真实表面的结构**,局部密度正常。

⇒ **"浮点"至少两类,判据不能混用。** track 延长对粗糙度**完全无效**(8.95→8.94):
它治"点被几个视角验证过",治不了"点本身位置准不准"。

### 🔥 极线带:生产已出货的刀,我一直没用

生产有 `aether_gpu_match_gemm_pairs_guided(guide_mode=1)` = E/F 极线带。

|---|---|---|

### ⚰️ WGSL FlashAttention:实测判负

`flash_attn.wgsl`(v1)/ `flash_attn2.wgsl`(v2)+ `wgsl_bench.py`(wgpu/Vulkan,5090)。
v1 只有 0.01–0.11 TFLOPS(耗时随 N **线性**而非 N² ⇒ GPU 没在算);
三条修法(BR 64→8 提并行度 / 累加器移出私有数组 / head 铺到 dispatch y 维)后 v2 快 8.6×,
但**天花板 1.25 TFLOPS,是 PyTorch SDPA(86.60)的 1/69**。

结构性原因:WGSL **无 tensor core、无 warp 级原语、共享内存 16KB 硬上限**
(CUDA 可用 48–164KB)⇒ 分块只能 8×24,K/V 反复重读。
⇒ 我此前记进总账的「WGSL kernel 1.8×」**应当划掉**。
