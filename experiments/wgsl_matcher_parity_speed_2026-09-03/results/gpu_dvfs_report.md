# Apple M3 Pro GPU 电源状态(DVFS)效应 — 立案报告

日期:2026-09-04  机器:Apple M3 Pro / macOS Darwin 25.1
测量者:全部在 Mac 上完成,**未启动任何 iOS app,未连接手机**。

---

## 0. 一句话结论(先给判决)

**这个效应对「WGSL 三端一套 vs 原生 Metal」的选型判断没有不利影响 —— 恰恰相反,它把两臂的差距压小了。**

DVFS 冷启是一笔 **3.5–4.0× 的乘性惩罚**(不是常数税,见 §5.6),两臂都落在这个带里:
WGSL **3.55×**、原生 **4.10×** ⇒ 两臂差距从稳态 **1.449×** 压到冷启 **1.301×**,**9/9 轮同号**。

机制已直接定罪(非推测):IOReport 的 `GPUPH` 通道显示慢的那几次 dispatch 就跑在
**P2/P3** 上,稳态是 **P13**,耗时与档位严格单调对应(§4)。

但它对**产品体感**很要紧:空闲 ≥250ms 后每次匹配按比例慢 3.5–4 倍;
而**唯一有效的缓解手段代价是让 GPU 常驻 92% 满载(实测 227× 空闲功耗)**,
与本项目「热稳定是硬约束」正面冲突,**不可用**。

⚠️ 绝对值口径:全部测量在**电池 + 低电量模式已开启**下完成(P14/P15 恒零,疑似被封顶),
接 AC 后需重测绝对值;**两臂对比不受影响**(同条件 ABBA)。iOS 侧完全未测。

## 1. 环境与污染说明(测量纪律)

- 全程 `uptime` load 2.6–4.0。测量期间发现的外部污染:
  - `swift-frontend` 99% CPU(会话开始时,瞬时,已消失)
  - `CoreDeviceService` 14–53% + `devicectl` 14% —— **不是我启动的**,是上一个会话遗留的
    `pkill` 清理脚本(`eval-xrslam-threading-backpressure-20260903`)。属 CPU 侧污染。
  - `WindowServer` 14–26%(常驻,GPU 合成器,不可避免)
- 所有 GPU 时长口径 = `cb.GPUEndTime - cb.GPUStartTime`(GPU 侧,不含 CPU 提交延迟)。
- 所有 A/B 采用**镜像交替 ABBA**,每臂各自享有**独立空闲期**
  (两臂不可能在同一次空闲后都是冷的 —— 第一臂跑完 GPU 就热了)。
- 报告中所有数字都带样本数与离散度。

### 仪器清单(本次新建,均在 `/private/tmp/mmaform/`)
| 文件 | 作用 |
|---|---|
| `idle.mm` → `idle` | 进程内空闲曲线:预热 → 睡眠 T → 逐次记录 dispatch |
| `idle_ps.mm` → `idle_ps` | 每次 dispatch 前后各采一次 IOReport,给出该次的性能态 |
| `iorep.c` → `iorep` | 只读 IOReport 探针(无需 sudo),读 GPU 性能态驻留 + 能量 |
| `mirror.mm` → `mirror` | **镜像 ABBA 双臂台架**:WGSL `cur` vs 原生 `pw_match_gemm2` |
| `ka.mm` / `kaw.metal` / `ka_sweep.mm` | keep-alive 占空比扫描(缓解手段实测) |
| `nat_gemm2.metal` | 从 `fair_match_native_arm` 二进制里抽出的**生产原生 MSL** |

**关键仪器进展:原生臂的 MSL 是以字符串字面量嵌在二进制里的**,我用
`python3` 按 NUL 边界抽出后 `xcrun metal -c` 零报错通过,并经独立核对确认它就是
`pwofficial_gpu_match.mm` 里的 `kGemm2KernelSrc`(`kernel void pw_match_gemm2`)。
**因此双臂镜像台架跑的是真正的生产原生核,不是替身。**
函数常量:`kPacked=false`、`kGuideMode=0`;threadgroup 内存为静态声明,无需 host 绑定。

## 2. 现象复现与定量

进程内复现(排除进程启动/管线编译混淆),`cur` 核,8192×8192:

```
空闲 0ms   : 6.892 6.475 6.738 6.946 6.152 6.971 ...   稳态 ≈ 6.5ms
空闲 20s   : 20.691 10.563 6.808 6.231 6.177 6.875 ...
空闲 20s   : 22.380  9.990 7.402 6.258 6.295 6.924 ...
```

**进程内比原始报告的效应更大**:首次 dispatch 20.7 / 22.4ms vs 稳态 6.5ms = **约 3.2–3.4×**
(原始报告的 ~2× 是因为跨进程 p50 把恢复期摊平了)。

**恢复极快**:第 2 次 ~10ms,第 3 次 ~7ms,第 4–5 次回到稳态。
即 **3–4 次 dispatch(约 35ms GPU 工作)** 就爬回满频。

## 4. 机制归因:直接看到了 GPU 性能态

### 4.1 有效探针:IOReport(**无需 sudo,无需改任何系统设置**)

`powermetrics` **不可用**(`sudo -n` 明确返回需要密码,按纪律未尝试)。
改用 `dlopen("/usr/lib/libIOReport.dylib")` + `dlsym`(该 dylib 在 dyld 共享缓存里,
磁盘上无文件但可正常 dlopen),订阅 `GPU Stats` 组,读 `GPUPH` 通道的
**16 档性能态驻留**(`OFF`, `P1`…`P13`)。

### 4.2 阳性对照(判据先过对照 —— 本项目铁律)

同一探针,三种已知条件,800ms 窗口:

| 条件 | GPUPH 驻留 |
|---|---|
| A. 空载 | `OFF=16897458 P1=2242271 P2=124485 P3=80038` |
| B. **持续 GPU 负载中** | **`P13=19375485`**(100% 驻留在 P13,`OFF` 归零) |
| B'. 复测 | **`P13=19361934`** |
| C. 负载结束 3s 后 | `OFF=15439517 P1=3904860`(回到基线) |

**探针在已知变化下确实会动,且方向、幅度、可逆性全部符合预期 ⇒ 判据成立。**

### 4.3 定罪:慢的那几次 dispatch 就是跑在低性能态上

`idle_ps`(每次 dispatch 前后各采一次),空闲 1000ms 后:

```

disp#1 gpu= 12.521ms  ps: OFF=43022 P1=1378 P2=142882 P3=163847
disp#2 gpu= 13.059ms  ps: OFF=42231 P1=1066 P2=190637 P3=118780
disp#3 gpu= 19.741ms  ps: OFF=7962  P1=1136 P3=389796 P5=92657
disp#4 gpu=  9.381ms  ps: OFF=18125 P1=1107 P5=211794 P7=13797
disp#5 gpu=  9.304ms  ps: OFF=28365 P1=1221 P5=134981 P7=93935
```

对照(**同样带采样开销**,空闲 0ms):
```
disp#0 gpu=  7.027ms  ps: P13=195893
disp#1 gpu=  6.209ms  ps: OFF=21711 P1=1603 P13=133353
disp#2 gpu=  6.307ms  ps: P13=171167
...全部 P13,6.2ms
```

**耗时与性能态严格单调对应:P2/P3 → 12–13ms,P5/P7 → 9.3ms,P13 → 6.2ms。**
机制定案:**GPU DVFS 降档,不是缓存、不是编译、不是额外工作量。**

> ⚠️ 探针侵入性说明:`idle_ps` 每次 dispatch 之间插入两次 IOReport 采样(每次数 ms),
> 这些间隙本身会阻止 GPU 爬到 P13,所以它给出的**绝对值被压扁了**(11–13ms 而非 22ms)。
> **它只用于证明机制,幅度以无插桩的 `idle` / `mirror` 为准。** 这是本探针的已知失真,不是发现。

## 5. 原生 Metal 臂是否同等受影响?(最重要的一条)

### 5.1 协议

`mirror` 台架,**同一进程内**加载两个管线,共用同一份真实夹具缓冲:
- WGSL 臂:`cur.metal`(tint 生成的 MSL)
- 原生臂:`nat_gemm2.metal`(**从生产二进制抽出的 `pw_match_gemm2`**)

每一个测量单元 = 该臂预热 25 次(取后 8 次做 warm)→ **该臂独享 2000ms 空闲** → 记录 5 次冷启。
轮次顺序 **ABBA / BAAB 交替**(偶数轮 `W N N W`,奇数轮 `N W W N`),共 10 轮。

先做 40 次双臂预热吸收一次性编译/分配成本,确保测的是 DVFS 不是初始化。

### 5.2 结果(n=14 wgsl / 15 native)

| WGSL p10–p90 | 6.36–6.86 | 19.52–25.34 | 9.55–10.29 | 6.60–8.30 | 6.22–6.85 |

### 5.4 两臂的惩罚量级

把冷启前 5 次相对各自稳态的超出量加总(n=20/臂):

| 臂 | 稳态 | 冷启额外 GPU 工作量总和 |
|---|---:|---:|
| WGSL | 6.764ms | **21.31ms**(范围 15.57–26.21) |
| 原生 | 4.604ms | **20.11ms**(范围 15.82–27.73) |
| 差 | | **+1.20ms**(远小于各自范围宽度) |

> ⚠️ **自我修正**:我一度想把这写成「≈20ms 的绝对常数税,与选哪一臂无关」。
> **这个说法被我自己的规模扫描推翻了**(见 §5.6):跨问题规模看,惩罚是**乘性**的而不是加性的。
> 这两臂的加性惩罚之所以接近,是因为它们的稳态耗时本来就只差 1.47×,不是因为存在什么常数税。
> 正确的说法是:**惩罚 ≈ 恒定倍数 3.5–4.0×,两臂都落在这个带里。**

### 5.5 对选型的结论

任务书里担心的情形是「原生受影响更小 ⇒ 记录在案的 1.57× 在断续场景下会更糟」。
**实测把这个担心证伪了,方向相反:**
- 相对倍数:原生 **4.10×** > WGSL **3.55×** ⇒ **原生受的相对冲击更大**
- 两臂差距:稳态 1.449× → 冷启 **1.301×** ⇒ **差距被压小**

**⇒ 该效应对选型是中性偏有利于 WGSL,不构成反对「三端一套 WGSL」的证据。**

诚实的强度界定:两臂的倍数(3.55 vs 4.10)都落在 §5.6 测到的 3.7–4.0 通用带里。
如果这个效应对所有核**完全等比**,那它对选型就是**严格中性**。
实测到的那点偏向 WGSL 的差(配对差 −0.505 ± 0.294,9/9 轮同号)是真实且可复现的,
但它小到不足以成为**支持** WGSL 的独立论据 —— 它只够用来**排除**「冷启会让 WGSL 更难看」这个反对意见。

### 5.6 规模扫描:效应是乘性的,不是加性的

`idle`,**WARM=400**(见 §5.7 为何必须这么大),每格 n=3,空闲 2000ms:

| NB | 稳态中位 | 稳态范围 | 冷#1 中位 | 加性税 | **倍数** |
|---:|---:|---|---:|---:|---:|
| 1024 | 1.831 | 0.771–3.307 ⚠️ | 3.296 | +1.47 | 1.80× ⚠️不可信 |
| 2048 | 1.661 | 1.506–1.691 | 6.493 | +4.83 | **3.91×** |
| 4096 | 3.367 | 3.062–3.434 | 13.558 | +10.19 | **4.03×** |
| 8192 | 6.918 | 6.262–7.714 | 25.798 | +18.88 | **3.73×** |

**加性税随核时长线性增长(4.8 / 10.2 / 18.9ms),而倍数几乎不变(3.7–4.0×)。**
⇒ 产品含义:**冷启是按比例罚,不是按次罚。** 把匹配拆小并不能摊薄这笔损失。

### 5.7 ⚠️ 副产品:一个会静默污染所有 GPU 台架的量尺陷阱

NB=1024 那一行的稳态范围是 0.771–3.307ms —— **4.3 倍的离散**。追下去发现:

| 预热次数 | NB=1024 的"稳态" |
|---:|---|
| WARM=30 | 1.117 1.117 1.241 1.283 1.406 1.283 |
| WARM=100 | 0.817 0.812 0.820 0.816 0.814 0.818 |
| WARM=300 | 0.817 0.821 0.746 0.744 0.814 0.744 |
| WARM=1000 | 0.770 0.829 0.821 0.815 0.842 0.826 |
| WARM=3000 | 0.830 0.836 0.824 0.833 0.818 0.815 |

**30 次预热得到的"稳态"比真稳态慢 37%,而且它看起来很稳(1.117/1.117/1.241),
不会以离散度的形式暴露出来。** 性能态读数证实:NB=1024 连续跑时驻留散布在
`P3/P5/P7/P9/P11/P13` 上,不像 NB=8192 那样干净地钉在 P13。

**定则:预热要按「累计 GPU 毫秒」算,不能按「次数」算。**
经验值:**预热必须累计 ≥300ms 的 GPU 工作**,否则测到的"稳态"其实是个低频数字。
- 现役 `bench13` 用 25 reps × ~7ms ≈ 175ms —— **在临界线以下,偏薄**,建议提高。
- 任何小核/小规模台架(<3ms/次)按次数预热几乎必然测出偏慢的假稳态。

这条与本项目既有的「尺子纪律」同族,建议进记忆。

> 生产 harness 侧校核(`fair_match_*_arm`,reps=20 warmup=5):
> WGSL `p50=7.426` / 原生 `p50=4.991` ⇒ 1.488×,与台架稳态 1.449× 一致,台架可信。
> ⚠️ 但 harness 的 `reps=8 warmup=0` **不能**用来测冷启:原生 rep0 = 96.5ms、WGSL rep0 = 19.5ms,
> 这里混进了**一次性进程初始化**(原生的初始化成本明显大得多),与 DVFS 无法分离。
> 这也是我不得不把原生 MSL 抽出来做进程内镜像的原因。

## 6. 缓解手段:实测 + 代价

### 6.1 实测一:极小 keep-alive dispatch —— **无效**

每 30ms 提交一次 1 threadgroup × 32 线程的空核:

| 条件 | GPUPH 驻留(1000ms 窗口) |
|---|---|
| keep-alive 30ms 间隔运行中 | `OFF=21705703 P1=2399390` |
| 无 keep-alive(对照) | `OFF=20818802 P1=3294667` |

**与不开 keep-alive 不可区分,都停在 OFF/P1。**
原因:DVFS 控制器是**利用率驱动**的,平凡 dispatch 的利用率 ≈ 0,只能把 GPU 从 OFF 拽到 P1,
**拽不到 P13**。网上常见的「提交一个小 keep-alive 核」建议在 Apple GPU 上**不成立**。

### 6.2 实测二:占空比扫描 —— 只有接近满载才有效

`ka_sweep`:在 2000ms 空闲窗口内以不同占空比跑 keep-alive,然后测真实核首次 dispatch。

轻载核(单次 0.090ms),3 轮:

| 占空比 | 首次 dispatch(3 轮) | 有效? |
|---:|---|---|
| 0%(纯睡眠) | 26.4 / 26.1 / 21.4 | 基线 |
| 0.1–1.2% | 19.5–26.8 | ❌ 无效 |
| 3.8–4.0% | 18.3 / 24.1 / 21.1 | ❌ 无效 |
| 36–52% | 22.5 / 23.8 / **6.4** | ❌ 不稳定 |

重载核(单次 3.583ms,2048 threadgroups),2 轮:

| 占空比 | 首次 dispatch | 有效? |
|---:|---|---|
| 0% | 21.3 / 18.5 | 基线 |
| 24–26% | 23.7 / 17.5 | ❌ 无效 |
| 47–49% | 10.8 / 21.5 | ❌ 不稳定 |
| **92%** | **6.39 / 6.87** | ✅ **完全有效(= 稳态)** |

**结论:要保住满频,必须把 GPU 按接近满载烧着。没有便宜的中间档。**

### 6.3 代价:实测功耗(IOReport `Energy Model` / `GPU Energy`,3s 等长窗口)

| 条件 | GPU Energy(3s) | 相对空闲 |
|---|---:|---:|
| 纯空闲 | 99,841,986 | 1× |
| 纯空闲(复测) | 171,103,116 | 1.7×(空闲本底离散度) |
| **92% keep-alive** | **30,729,182,512** | **≈ 227×** |
| 真实匹配核连续满载(上限参照) | 33,470,881,568 | ≈ 247× |

**keep-alive 的功耗 = 真实满载的 92%。** 也就是说:
为了省下一次冷启的 ~20ms,要付出「**GPU 一直按满载跑**」的功耗与发热。

对本项目这是**否决性**的:
- 记忆里「热稳定是硬约束」「采集时长是产品指标」;
- 手机上 GPU 满载常驻会直接吃掉采集时长,并触发既有的热降频闸
  (`OFFICIAL_AETHER_MATCH_GAP_SERIOUS_PCT` 那条链路);
- 净效果是**为了省 20ms 而让整条采集更慢更热** —— 收益 20ms,代价是数分钟级的热预算。

**⇒ keep-alive 不可用。**

## 7. 缓解手段调研(一手来源)

### 7.1 Metal 有没有官方的性能态/升频提示 API? —— **没有**

对本机 Xcode 26.2 的 macOS + iPhoneOS SDK `Metal.framework/Headers/` 全部 96 个头文件做穷尽 grep:
`powerState` / `throttle` / `dvfs` / `boost` / `idle` / `governor` / `pstate` **全部 0 命中**。
两个 SDK 的头文件列表 `diff` 无输出 ⇒ **iOS 侧同样不存在**。

逐条裁决任务书点名的候选:

| 候选 | 实际是什么(头文件实证) | 与 DVFS |
|---|---|---|
| `MTLResidencySet`(macOS 15/iOS 18) | 资源/堆的**内存驻留**(页表 wiring) | ❌ 无关 |
| `shouldMaximizeConcurrentCompilation` | `MTLDevice.h:1292` —— **CPU 侧**着色器编译线程数,且 `API_UNAVAILABLE(ios)` | ❌ 无关 |
| `MTLCommandQueueDescriptor` | 只有 `maxCommandBufferCount` + `logState` | ❌ 无关 |
| `MTLCommandBufferDescriptor` | `retainedReferences` / `errorOptions` / `logState` | ❌ 无关 |
| queue/buffer priority | Metal 里唯一的 priority 是 `MTLIOPriority`(资源加载 IO 队列) | ❌ 无关 |
| Game Mode (`LSSupportsGameMode`) | 讲的是**优先级与后台抑制**,Apple 从未声称它提高 GPU 时钟;且要求 app 声明为游戏类别 | ❌ 不适用 |
| Sustained Execution Mode(`com.apple.developer.sustained-execution`) | Apple 文档明说它**限制突发性能**,把表现钉在 steady state 以便可复现 | ❌ **方向相反,会更慢** |

**Apple 官方两次书面确认没有这个 API:**
- Developer Forums thread **702651**(2022-03):提问者问的正是"能不能提示 GPU 提前升频",
  Apple 图形工程师回答**目前没有办法**,只提到 GPU 工具里有 performance state inducer。
  https://developer.apple.com/forums/thread/702651
- Developer Forums thread **768160**(2024-11 ~ 2025-05):开发者报告 macOS Metal compute 场景下
  系统始终不升频,用 Instruments 手动锁 Maximum 后**快 2×**。
  Apple DTS 工程师回复承认这是 API 与性能的改进机会,请走 Feedback Assistant;2025-05 确认"在调查中"。
  https://developer.apple.com/forums/thread/768160

**唯一能设 performance state 的官方途径是三个调试工具**(Instruments Recording Options、
Metal Debugger 的 GPU Profiler、Xcode Devices and Simulators → Device Conditions → GPU Performance State),
**都不能进出货代码**。来源:WWDC21 Session 10157
(https://developer.apple.com/videos/play/wwdc2021/10157/)、
Apple《Optimizing GPU performance》
(https://developer.apple.com/documentation/xcode/optimizing-gpu-performance)。

WWDC21 10157 同时确认:performance state 由 OS 管理,受**器件温度、系统设置、GPU 利用率**等影响 ——
**"GPU 利用率"这一条正是我们这个场景**。

### 7.2 机制交叉验证:Asahi Linux 逆向出的调速器参数,与我们的实测吻合

Apple GPU 的 DVFS 跑在 GPU 自带的协处理器上。Asahi Linux 的 Rust DRM 驱动
(`drivers/gpu/drm/asahi/hw/mod.rs`)与 Apple 固件设备树给出了调速器结构:
它是一个 **PID 控制器**,关键参数(M1 / t8103 的公开 dts 值):

| 参数 | 值 | 含义 |
|---|---|---|
| `apple,perf-tgt-utilization` | **85** | **目标 GPU 利用率 85%** |
| `apple,power-sample-period` | **8** | **8ms 采样周期** |
| `apple,perf-filter-time-constant` | 5 / 50 | 两级滤波时间常数 |
| `apple,perf-base-pstate` | 1 | 起始档 = P1 |
| `perf_boost_min_util` | (字段存在) | 升档所需的最小利用率 |
| `idle_off_delay_ms` / `fw_early_wake_timeout_ms` | **公开 dts 里没有** | 空闲降档延时 —— 见 §8 死角 |

来源:https://github.com/AsahiLinux/linux/blob/asahi/drivers/gpu/drm/asahi/hw/mod.rs
与 `arch/arm64/boot/dts/apple/t8103.dtsi`。

**这解释了我实测到的两件事,而且是独立得来的:**
1. **8ms 采样 × 几个采样周期爬阶梯 ≈ 我测到的 35ms / 3–4 次 dispatch 恢复。** 数量级吻合。
2. **目标利用率 85% ≈ 我测到的"要 92% 占空比才有效"。**
   这正是为什么极小 keep-alive(利用率 ≈ 0%)完全无效 —— 它够不着 85% 这条线。
   两条证据来路完全不同(我的是黑盒计时,Asahi 的是固件参数),结论一致。

⚠️ Asahi 不支持 M3,上述数值是 **M1** 的;M3 Pro 的具体参数无公开来源。

### 7.3 业界实践:真正出货 keep-alive 的只有一家,而且它在 Pro/Max 上失效

| 框架 | 有没有 GPU 冷频 keep-alive? |
|---|---|
| **llama.cpp** | ❌ **有个叫 `keep_alive` 的东西,但那是内存驻留,不是时钟**。`ggml-metal-device.m` 里的后台心跳线程周期性调 `MTLResidencySet.requestResidency`,防止 OS 回收 wired 内存(`GGML_METAL_RESIDENCY_KEEP_ALIVE_S`,默认 3 分钟),**不提交任何 GPU 工作**。另有 `common.cpp:1511` 的一次性空 decode warmup,治的是建图/建 pipeline/页入,**非周期、与 DVFS 无关**。把这段当"llama.cpp 有 GPU 保活 dispatch"是误读。 |
| **MLX** | ❌ GitHub code search:`warmup` 命中全在 `benchmarks/`,`mlx/backend/metal/` **0 命中** |
| **PyTorch MPS** | ❌ `aten/src/ATen/mps` 下 `warmup` **0 命中** |
| **ncnn** | ❌ `warm_up` **0 命中** |
| **Anukari**(商业音频插件) | ✅ **唯一真实出货的**:常驻一个 warp 跑空转 spin kernel,M1 上音频延迟降约 40% |

**Anukari 的经验里有两条对我们直接致命:**
- 作者明确记述该 spin loop **在 Pro/Max 变体上失效**,推测因为每个 GPU chiplet 独立调频。
  **我们这台正是 M3 Pro** —— 与我实测「轻量 keep-alive 全线无效、要 92% 占空比才行」一致。
- M4 Max 上 Metal 会把排队的 spin kernel 并行化反而抢占正常工作,得用 `MTLEvent` 强制串行。
- 作者自评这是他"出货过的最蠢的代码";**Apple DTS 明确不推荐**这种做法。
  来源:https://anukari.com/blog/devlog/waste-makes-haste 、
  https://anukari.com/blog/devlog/apple-performance-progress

### 7.4 功耗代价的旁证

Apple 从不公布 P-state 功耗曲线(**死角**)。第三方 `powermetrics` 测量:
- **M3 Pro GPU 满载 ~18–24W**,idle 接近零(https://eclecticlight.co/2024/02/23/apple-silicon-2-power-and-thermal-glory/ ,
  https://eclecticlight.co/2025/01/06/power-modes-and-apple-silicon-gpus/)
- Low Power Mode 在 M4 Pro 上把 GPU 从 1578→1056 MHz(-33%),功耗 ~20W→~6W

**与我实测的 227× 空闲功耗对照**:keep-alive 的能耗 = 真实满载的 92%,
换算即 **~17–22W 常驻**。这与"为省 20ms 而全程满载"的定性判断一致。

## 9. 建议(供裁决,未执行)

1. **不要上任何 keep-alive。** 实测代价 = GPU 常驻 92% 满载(227× 空闲功耗),与"热稳定是硬约束"正面冲突。
2. **选型不变。** WGSL 三端一套的判断不受这个效应影响;冷启只会让两臂差距**变小**。
3. **真正合法的缓解方向是"别让 GPU 进空闲"**,而不是"空闲时假装忙":
   合并 dispatch、消除 GPU timeline gap、把匹配与相邻 GPU 阶段排到一起。
   这也是 Apple 自己在 WWDC22《Scale compute workloads across Apple GPUs》里给的方向。
   **注意这是方向不是方案,上机前要单独立项测。**
4. **接 AC 电重测一遍绝对值**(§8.1),确认 LPM 封顶对 250ms 阈值和 3.7–4.0× 倍数的影响。
5. **产品体感层**:如果采集期两次匹配间隔 >250ms,每次都会吃满这笔乘性惩罚。
   要不要在 UI 上做预期管理,或把匹配节奏压到 250ms 以内,是产品决策不是技术决策。
6. **把 §5.7 的预热定则进记忆**:预热按累计 GPU 毫秒算(≥300ms),不按次数;
   现役 `bench13` 的 175ms 偏薄,建议提高。

## 10. 一句话结论

> **这个效应对「WGSL 三端一套 vs 原生 Metal」的选型判断没有不利影响。**
> DVFS 冷启是一笔 **3.5–4.0× 的乘性惩罚**,两臂都落在这个带里;
> 实测 WGSL 3.55× 略优于原生 4.10×,使两臂差距从稳态 **1.449×** 压到冷启 **1.301×**(**9/9 轮同号**)。
> 它**够格**排除"冷启会让 WGSL 更难看"这个反对意见,但**不够格**成为支持 WGSL 的独立论据。
> 真正要紧的是产品体感:断续调用时每次匹配按比例变慢 3.5–4 倍,
> 而**唯一有效的缓解手段代价是让 GPU 常驻满载(227× 空闲功耗),在本项目的热约束下不可用。**
