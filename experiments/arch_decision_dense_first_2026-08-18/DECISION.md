# 架构决策书:稠密优先管线(2026-08-18,用户已拍板)

一天之内四条实验线收敛出的架构重塑。**每一条决策都有当日实测背书,无一条是估的。**

## 决策(用户逐项拍板的原话依据)

| # | 决策 | 用户拍板 |
|---|---|---|
| D1 | **稀疏点云从交付物降级为内部位姿引擎**,用户永远不看它 | "如果直接没有稀疏,这对于用户才是最省时间的方案" |
| D2 | **位姿引擎 = GTO(极线门控匹配)**,LightGlue 退役 | "可以用GTO" |
| D3 | **预览 = 抽稀稠密**(并集方案否决:稀疏补丁会把浮点带回来) | "稠密好就是因为它几乎没有任何浮点" |
| D4 | **选区 UX 落在抽稀稠密上**(选区功能保留,载体不再是稀疏) | "稀疏点云的选区部分肯定要保留" |
| D5 | **稠密在拍摄期流式生长**(逐帧,尾随相机),拍完只收尾 | "需要每帧都更新" |

```
拍摄期   live稀疏(现有流式SfM,即时反馈层,不动)
         + GTO匹配(~10ms/对) + 深度推理摊平 + 冻结即融合(尾随生长,逐帧可见)
拍完     尾部重融+首融 82帧 ≈ 17s + 快速导出 ≈ 1s + 抽稀 0.3s   ← 用户等的全部
交付     稠密(逐字节=官方全量融合) → TSDF
```

## 证据链(全部当日实测)

### E1. GTO 位姿对稠密无损(掉换位姿引擎的安全性)
b28,132 帧,固定扩散噪声(seed=20260818+帧号,逐比特),官方 filter_depth,单变量=位姿:

| 相对 dense_P16k(30,640,053 点) | 点数 |
|---|---|
| P8k(预算效应) | −6.25% |
| P16kH(噪声地板) | −2.67% |
| **GTO** | **+0.79%(地板内,正向)** |

gauge 残差:GTO↔P16k **2.08mm** < 两次 LightGlue 建图互差 2.21mm ——
**对稠密而言 GTO 与 LightGlue 是同一套位姿**,而它匹配便宜 4.2×(10.2 vs 43.2 ms/对)。
肉眼终审:用户对同点数抽稀 A/B(compare_pose.html)放行。

### E2. 流式调度 = 官方全量的逐字节等价(零口径偏离)
策略:邻居集(pair.txt top-10,**有序**)连续 M=10 步不变即冻结融合;拍完后凡最终列表
≠冻结列表的 ref 重融。MD5 对拍:

```
stream_P16k.ply  = 1d65b598969866c99853f0ed755820d8
dense_P16k.ply   = 1d65b598969866c99853f0ed755820d8   (官方全量)
```

实测调度:拍摄期融 109/132(冻结步 min 22 / 中位 70 / max 130),
尾部 59 重融 + 23 首融 = 82 帧 × 209ms ≈ **17.1s**。
等价性由"变了就重融"兜底,与冻结策略无关(M 可再调,只影响尾部账)。

⚠️ 两条口径铁则(违者对不上官方):
1. **重融判据比有序列表不比集合**——filter_depth 深度平均按源视图次序浮点累加。
2. **共视打分必须用官方 calc_score 语义**:同一 3D 点在同图多个 2D 观测(track 合并)时
   官方只乘小下标图的重数;`mvs_channels.view_scores` 的 occ_i×occ_j 口径会把 **44% 的
   ref 的 top-10 排错**(pair(0,2) 实测 3696.40 vs 3976.46)。已修的向量化版:
   `streaming_fuse_md5_20260818/code/schedule_sim.py`。

### E3. 融合可流式且拍完 30s 有余量(Mac 锚点)
官方 filter.py 结构零全局归约(每 ref 只依赖自己六类输入 + top-10 邻帧深度图)。
官方跑法 76.9s 中 **62% 是导出代码的 Python 逐点 tuple 循环**——列赋值替换后输出
**MD5 相同**,46.6s→0.5s。真融合数学 27.6s(209ms/帧)。
抽稀导出(30.6M→30 万)0.3s。

### E4. 推理锚点与真机悬念
M3 ORT-WebGPU 实测 **528.7 ms/帧**(与 08-17 fixture97 的 538ms 互证)。
拍 2 分钟/132 帧 ⇒ 摊平预算 909ms/帧:M3 余量 1.72×,富余 380ms/帧×132≈50s
可吸收 59 帧的重推理+重融修复。
**A16 外推 1322–2115ms 横跨预算线——真机 A4 打点是全架构唯一剩余悬念**
(iOS 构建卡 ORT #32147,补丁已验证)。iPhone 11 外推 2.6–6.3s,任何口径进不去。

### E5. 稀疏预算对稠密无影响(前置定案,当日)
P16k vs P8k 稠密:点数 −6.25%、覆盖 −1.3~−4.2%、粗糙 +1.08%,**每一档都小于噪声地板**
(P16kH:覆盖 −5.6~−8.3%)⇒ 稀疏关键点预算只服务位姿,16384 之争对成品无意义。
(⚠️ 跨重建逐视图对拍必须按 image.name 配对——按 images.bin 下标=注册顺序会得出
19%/0-132 的假差异,两次建图仅 6.1% 同位同名。)

## 为什么 LightGlue 可以退役(完整因果)

1. 它的稀疏云确实最好看(用户肉眼:"惊艳来自匹配器"——ALIKED+暴力覆盖塌到 0.34×,
   门控宽口径浮点海,严口径覆盖掉到 0.60×);
2. 但架构重塑后稀疏云**不再需要好看**(D1/D3),只需要位姿准;
3. GTO 位姿与 LightGlue 等价(E1)且便宜 4.2×;
4. 注意力墙(66.1% 且 fp32/fp16/compile 三测纹丝不动)本来也堵死了 LightGlue 上机的路
   (缺口 20–60×,17 试 16 负,见 lightglue_spike_2026-08-18/README)。

## 未决项(按优先级)

1. 🔴 **A4 真机打点**(A16 ORT-WebGPU ms/帧)——全架构 go/no-go,需用户手机配合。
2. 🔴 **iPhone 11 下限策略**——降档口径(降分辨率/减 num_view/关键帧更稀)或退出 30s 承诺,须用户拍板。
3. 🟡 冻结策略调优(M=10 重融率 59/109 偏高;等价性不受影响)。
4. 🟡 手机融合的工程化:float32/分块累积(Mac 峰值 RSS 4.35GB,iPhone 11 共 4GB 装不下;
   逐帧工作集仅 ~40MB,结构可行)、mask PNG 关闭、src 深度 LRU。
5. 🟡 拍摄期修复(邻居变更帧的重推理+重融)在 A16 余量内是否成立——同样等 A4 数字。
